# v2 — deck-conditioned advice

Grades that account for the deck you actually have, rather than a card's
standing in the abstract. Deferred from v1 by choice; this is the groundwork.

## The finding this rests on

Spire Codex's `POST /api/draft-advice` looks like an opaque server-side model.
Probing established that it is not:

```
score(c) = base(c) · ∏ lift(h, c)   for h in the set of cards held
```

Three properties came out of that, and each one matters:

- **Exactly multiplicative.** Nine of ten offers against a forty-card deck
  matched to four decimal places. The tenth had the most reasons, which revealed
  that the API truncates its own reasons list at five *while scoring with all of
  them*. An offline reimplementation is therefore more faithful than the
  response body.
- **Pairwise and context-free.** A one-card deck returns the identical lift a
  twelve-card deck does. This is what makes harvesting possible: ask "what is
  everything worth if I hold exactly this one card" once per card, and the whole
  model falls out.
- **Duplicate-insensitive.** One, two or three copies produce the same score.
  The model dedupes to a set.

The consequence is that v2 needs no architectural change and no network access
at play time. It is a second build-time harvest and a product over a bundled
table — the same shape as the tier list.

| The bundled `lifts.tsv` | not harvested |
| Anything in the HUD | not started |

Ten tests pin the three properties above, plus reason ordering and the
truncation rule. They use synthetic tables: the maths is what is being asserted,
and it can be asserted without the real data.

## What is left, and what to watch for

**Run the harvest.** One request per card plus a baseline, paced from Codex's
published limits. It is deliberately outside the weekly refresh.

```powershell
dotnet run --project tools\FetchCodexData -c Release -- --harvest-lifts
```

Interrupting is safe. It checkpoints after every row and resumes where it left
off, so a dropped connection or a closed terminal costs one repeated request
rather than the whole run.

### Why it cannot be fewer requests

This is the obvious thing to want to optimise, so the answer is written down.

One request asks "given I hold exactly these cards, what is everything worth",
so `deck=[h]` against every offered id returns a whole **row** — about 500 lift
factors from a single call. The offered axis is already fully batched.

Batching the *deck* axis does not work. In logs, a request with deck subset `S`
returns, for each candidate `c`, the sum of `log lift(h, c)` over `S`. That is
one linear measurement per column, and every column shares the same measurement
vector. Recovering a dense column of N unknowns needs N independent
measurements, so **N requests is the floor for exact recovery** — a property of
the problem, not of the implementation.

Sparse recovery could beat that bound in principle, since most pairs do not
interact. It is not attempted: it would rest on a sparsity nobody has measured,
and on summing hundreds of logs without the API's rounding eating the signal. A
one-off half hour is cheaper than being subtly wrong.

### How long

| Tier | Requests/min | ~503 requests |
| --- | --- | --- |
| general (unregistered — what we have) | 15 | ~34 min |
| registered | 60 | ~8 min |
| academia | 100 | ~5 min |
| paid | 120 | ~4 min |

The tool reads the live figure from `/api/rate-limits` and paces to it. Pass
`--tier registered` if Codex ever grant a higher one; there is no API-key
mechanism in their OpenAPI document today, so the general tier is what an
automated caller gets.

**The response shape is unverified.** Codex's OpenAPI document declares no
response schema for this endpoint, and their API was unreachable when the
harvester was written, so the field names are inferred. The parser tries the
plausible spellings and prints the raw body when none matches — the first real
run either works or tells you exactly what to change. Fix it in
`HarvestLifts.ListFields` / `IdFields` / `ScoreFields`.

**Size needs a decision.** The harvest prints a density figure when it finishes
— the share of the ~253,000 possible pairs that actually move a score. That is
the number to decide on. ~500 cards squared is 250,000 possible pairs. Only
pairs that actually move a score are kept — a factor of exactly 1 is the same as
no entry — so the real number depends on how sparse the model turns out to be.
If it lands in the low thousands, a TSV bundles fine alongside the ratings. If
it is much denser, this is the point to compress, and the decision should be
made against the measured size rather than guessed at now.

**Relics are in scope and were not in the original analysis.** The request
schema takes `deck` as `"cards:ID"` / `"relics:ID"`, with bare ids defaulting to
cards. Holding a relic can therefore change a card's score, and the harvest as
written covers cards only. Worth extending once the card model is confirmed
working.

## Rate limits

Codex's terms say 60–120 requests/minute, but their live `/api/rate-limits`
reports 15/minute per endpoint for an unregistered caller. Respect the lower
figure — a harvest is the heaviest thing Ossuary ever asks of them, and it is
the one place where being careless would be noticed. Registering for the 60/min
tier before harvesting would be the polite move.
