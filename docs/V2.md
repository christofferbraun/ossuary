# v2M0 — deck-conditioned advice

Grades that account for the deck you actually have, rather than a card's
standing in the abstract. Deferred from v1 by choice; this is the groundwork.

## The model

Codex documents `POST /api/draft-advice` as:

> Each offered card starts at its baseline take-rate and is nudged by the lift
> of every held item that lists it (**per-term clamped, naive-Bayes-style**), so
> the result reflects what players who reached this state actually pick.

So the shape is a product of per-pair factors over the held set:

```
score(c) = base(c) · ∏ f( lift(h, c) )   for h in the set of items held
```

`Ossuary.Advice.DeckAdvice` currently implements `f` as the identity — a plain
product. **That is known to be incomplete.** "Per-term clamped" means each
factor is bounded before it is multiplied in, and the bound is not published.
Without it, a deck holding many mildly synergistic cards will drift further from
Codex's own answer the larger it gets.

This is the first thing to measure once a harvest exists: score a few decks
offline, compare against `POST /api/draft-advice` for the same deck, and fit the
clamp from the disagreement. Until then, treat the offline scores as a ranking
rather than as a reproduction of Codex's numbers.

### A note on provenance

An earlier version of this document reported that probing had *established* the
model was exactly multiplicative, pairwise, and duplicate-insensitive, citing
"nine of ten offers matching to four decimal places". Nothing in this repository
reproduces that experiment and no harvest has ever been run, so those claims are
recorded here as hypotheses rather than findings. The documented clamp above is
direct evidence that at least the first of them is not exactly right.

The tests pin the *maths as implemented*, not the API's behaviour. They use
synthetic tables, which is the right thing for asserting arithmetic and no
evidence at all about Codex.

## Harvesting

### The endpoint

`GET /api/draft-recs/{item_type}/{item_id}`:

> Given a card/relic you already have, the cards players most often draft when
> offered them, ranked by lift over each card's baseline take-rate. Each entry
> carries `pref`, `pref_base`, `lift`, `offers` (sample size), and `winrate`.
> Empty `recommends` until the build job has run.

That is the lift table, one row per held item, stated as such — and it returns
`lift` **directly**.

The earlier design probed `POST /api/draft-advice` with single-card decks and
divided by a baseline, recovering each lift by inference. Same request count,
but it depended on the multiplicative assumption being exact and on field names
the endpoint does not document. Reading the published number instead removes
both problems, and covers **relics**, which deck-probing could not reach —
relic synergies are a large part of what makes advice deck-specific at all.

### Probe before you harvest

One request. Prints the raw response and what the parser made of it.

```powershell
dotnet run --project tools\FetchCodexData -c Release -- --probe-lifts
```

Do this first, every time there is any reason to think Codex has changed. The
field *values* are documented; the container is not — `recommends` could be a
map keyed by id or a list of objects carrying one, and both are handled. The
probe settles it for the price of one request instead of a whole run.

### Then harvest

```powershell
$env:CODEX_API_KEY = '...'
dotnet run --project tools\FetchCodexData -c Release -- --harvest-lifts
```

Interrupting is safe. It checkpoints after every row and resumes where it left
off, so a dropped connection or a closed terminal costs one repeated request
rather than the whole run.

### Why it is one request per item

This is the obvious thing to want to optimise, so the answer is written down.

Each held item's row is an independent set of numbers. There is no request that
returns two rows, so N items means N requests. The offered axis is already
fully batched — one call returns every partner for that item.

The only bulk alternative Codex offers is `GET /api/exports/runs`: the entire
submitted-run corpus as gzipped JSONL, cursor-paged, each line a full raw game
JSON including `deck`, `relics` and `card_choices`. Lifts could be recomputed
from it. That trades several hundred small requests for a multi-gigabyte
download **and** a reimplementation of Codex's model — and it would be our
model, not theirs, which defeats the point of matching their advice. It is the
right tool for a different question, not for this one.

### How long

| Tier | Requests/min | ~800 requests |
| --- | --- | --- |
| general (un-keyed) | 15 | ~61 min |
| registered (with a key) | 60 | ~15 min |
| academia | 100 | ~9 min |
| paid | 120 | ~8 min |

~800 is cards plus relics from the bundled table. The tool reads the live figure
from `/api/rate-limits` and paces to it, with a 15% margin because limits are
usually enforced over a sliding window.

## The API key

Codex's `/api/rate-limits` documentation says it plainly:

> Browse = un-keyed traffic (per IP); keyed tiers apply per `X-API-Key`. All
> caps count per endpoint.

So a key moves us from 15/min to 60/min — a harvest from an hour to a quarter of
an hour.

**Setting it up.** The key is read from the `CODEX_API_KEY` environment
variable and sent as the `X-API-Key` header. It is never committed and never
passed on the command line, where it would end up in shell history and in CI
logs.

- **Locally**: `$env:CODEX_API_KEY = '...'` before running the tool.
- **In CI**: a repository secret named `CODEX_API_KEY`
  (*Settings → Secrets and variables → Actions → New repository secret*).

With a key present the tool paces to the `registered` tier by default; without
one it stays on `general`. `--tier` overrides, for if Codex ever grant
something higher.

The key gates *nothing but the rate*. Every endpoint used here is public, so a
harvest with no key produces exactly the same table, more slowly.

## The workflow

`.github/workflows/harvest-lifts.yml`, manual dispatch only — never scheduled.
This is the heaviest thing Ossuary asks of Codex, so it runs when a person means
it to.

Two modes:

| Mode | Cost | What it does |
| --- | --- | --- |
| `probe` | 1 request | Fetches one row, prints the raw body and the parse |
| `harvest` | one per card and relic | The full table, then opens a pull request |

The checkpoint directory is cached between attempts and saved **even when the
job fails**, which is the point: a failed harvest resumes rather than starting
over. `fresh: true` discards it.

A `concurrency` group prevents two harvests overlapping — they would race on the
checkpoint and, worse, each would think it had the whole rate budget.

## Still to decide

**The clamp.** See the top of this document. This is the substantive open
question, not a detail.

**Size.** The harvest reports how many pairs survived the sample floor and the
"actually moves a score" filter. If that lands in the low thousands, a TSV
bundles fine alongside the ratings; if it is much denser, this is the point to
compress. Decide against the measured number rather than guessing now.

**An empty table is a real outcome.** Codex says recommendations are empty
"until the build job has run". A harvest that returns nothing everywhere means
their model has not been built, not that ours is broken — the tool counts empty
rows and says so.

## Rate limits

Codex's written terms quote 60–120 requests/minute; their live
`/api/rate-limits` reports 15/minute per endpoint for an un-keyed caller. Where
the two disagree, respect the lower one. Caps count **per endpoint**, which is
why the weekly ratings refresh is comfortable — seven requests spread over six
endpoints — and why the harvest is not: every one of its requests hits
`/api/draft-recs`, so the whole budget applies to it and pacing is the entire
problem.
